11주차 · Module 11

시퀀스 제어 프로그래밍 실습

가상 이송·검사 장치로 설계부터 정상·고장 시험까지 완성한다

오늘의 학습 목표

  • 요구사항을 단계표·전이 조건·고장 처리로 정리한다.
  • FB·Static·인스턴스 DB와 TON을 사용해 시퀀스를 구현한다.
  • 시작 에지·정지·Reset·고장의 우선순위를 구분한다.
  • 정상·경계·고장 시나리오를 시험하고 결과를 기록한다.

선수학습: 7~10주차 / 대상: TIA Portal S7-1200·S7-1500 지원 환경 / 방식: 내부 DB 기반 시뮬레이션 / 실제 I/O 및 안전 제어 제외

1

실습 목표와 가상 장치

이번 실습에서는 제품을 이송하고 정해진 시간 동안 가상 검사를 수행한 뒤 완료를 표시하는 시퀀스를 작성합니다. 7주차 SCL 조건문, 8주차 단계 설계, 9주차 프로젝트 구성, 10주차 CPU 확인을 하나의 프로그램으로 연결합니다.

모터·센서·검사기는 모두 내부 DB 태그로 표현합니다. 실제 출력은 연결하지 않습니다. 장치의 동작 순서를 설계표로 먼저 정하고, FB에 상태와 타이머를 저장한 다음 정상·정지·고장 시나리오를 시험합니다.

실습 결과물: 단계 설계표 + FB_Sequence + 인스턴스 DB + LabSeq DB + 시험 결과표
실제 장치를 제어하는 완성 프로그램이 아닙니다. 비상정지·안전문·안전 정지는 일반 Bool 입력과 SCL 조건만으로 구현하지 않습니다. 실제 모터 기동·정역·인버터 제어는 12주차 주제와도 구분합니다.
2

요구사항 — 정상 운전과 예외를 함께 정의

  1. 대기 상태에서 시작 버튼의 새로운 상승 에지가 있어야 운전을 시작합니다.
  2. 실행 허가 Permit이 TRUE이고 위치 센서가 FALSE일 때 이송을 시작합니다.
  3. 5초 이내 제품 위치 센서가 TRUE가 되면 이송을 멈추고 가상 검사를 시작합니다.
  4. 위치 센서가 TRUE인 상태에서 2초간 검사 후 완료 상태로 이동합니다.
  5. 완료 표시와 완료 횟수는 Reset 또는 ClearCount 정책에 따라 처리합니다.
  6. 일반 정지 StopReq는 시퀀스를 중단하고 대기로 돌려보냅니다. 이어서 재개하지 않습니다.
  7. 실행 허가 상실·이송 시간 초과·검사 중 위치 상실은 고장 상태에 저장합니다.
  8. 고장은 원인 확인 후 Reset으로 해제하며, 새 Start 없이는 재가동하지 않습니다.
2초 검사는 실제 품질 판정이 아니라 시간 기반 모의 동작입니다. 모든 제품이 통과했다고 가정하지 않으며 “검사 시간 완료”만 의미합니다. 5초 제한도 교육용 임의 값입니다.
3

ResetBool초기화·고장 해제 요청

전역 DB LabSeq에 위 Input·Output과 같은 이름·자료형의 변수를 만듭니다. 이 DB는 감시 테이블에서 조작·관찰할 가상 장치 인터페이스입니다. 물리 주소 %I·%Q와 연결하지 않습니다.

입력 Bool의 초기값은 모두 FALSE로 설정합니다. 실습 시작 시 Permit을 TRUE로 하고 Reset을 한 번 입력해 의도한 대기 상태를 확인합니다.

State를 CASE로 한 번 평가하므로 정상 순서의 단계 전이는 한 FB 호출당 최대 한 번입니다. 단계 전이 후 최종 출력을 계산하여 이송에서 검사로 넘어간 스캔에 MotorCmd가 OFF가 됩니다.

5

우선순위와 재시작 정책

우선순위조건처리
1NOT Permit900으로 이동, 코드 1 저장
2ResetPermit이 있으면 대기·고장 해제
3State=900고장 유지, StopReq로 지우지 않음
4StopReq진행 중 시퀀스 취소, 대기
5정상 CASE 처리단계별 전이·타임아웃 검사

고장 우선순위도 명시합니다. 이송 제한 시간과 위치 센서가 같은 스캔에 성립하면 시간 초과를 우선합니다. 검사 중 위치 상실과 검사 시간 완료가 동시에 성립하면 위치 상실을 우선합니다.

StopReq는 일시정지/재개가 아니라 취소입니다. Reset은 새 운전 시작 명령이 아닙니다. Start를 누른 채 StopReq나 Reset을 해제해도 새 상승 에지가 없으므로 자동 시작하지 않습니다.

고장 코드는 최초 원인을 유지합니다. 이미 고장인 상태에서 Permit이 추가로 사라져도 최초 코드를 덮어쓰지 않습니다. 원인을 제거해도 Reset 전에는 고장 상태를 유지합니다.

6

FB 인터페이스와 인스턴스 구성

SCL 언어의 FB_Sequence를 추가하고 섹션 3의 Input·Output을 선언합니다. 다음 항목도 선언합니다.

구분이름자료형·시작값
StaticStateInt, 0
StaticErrorCodeInt, 0
StaticCountValueDInt, 0
StaticPrevStartBool, FALSE
StaticMoveTimer, InspectTimer각각 IEC TON 멀티인스턴스
TempStartEdgeBool
  1. FB 본문에 TON 명령을 삽입하고 Multi-instance를 선택합니다.
  2. 이름을 MoveTimer로 정하고 생성되는 Static 선언을 확인합니다.
  3. 별도 TON을 추가하여 InspectTimer를 만듭니다.
  4. 주기 프로그램에서 FB를 호출하고 인스턴스 DB DB_Sequence를 생성합니다.
  5. 입출력을 LabSeq DB에 연결하여 매 스캔 호출합니다.
타이머 저장 구조·자료형·호출 표기는 TIA Portal과 CPU에 따라 확인해야 합니다. 편집기가 생성한 호출과 선언을 우선하세요. 한 타이머 인스턴스를 두 용도로 재사용하지 않습니다.
7

전체 SCL 코드 — FB 본문

// 1. 상승 에지: Stop/Reset 중에도 매 스캔 갱신
#StartEdge := #Start AND NOT #PrevStart;
#PrevStart := #Start;

// 2. 타이머는 매 스캔 호출
#MoveTimer.TON(
    IN := (#State = 10) AND #Permit AND NOT #StopReq AND NOT #Reset,
    PT := T#5s);
#InspectTimer.TON(
    IN := (#State = 20) AND #AtPosition AND #Permit
          AND NOT #StopReq AND NOT #Reset,
    PT := T#2s);

// 3. 우선순위: 허가 > Reset > 고장 유지 > 정지 > 정상
IF NOT #Permit THEN
    IF #State <> 900 THEN
        #ErrorCode := 1;
    END_IF;
    #State := 900;
ELSIF #Reset THEN
    #State := 0;
    #ErrorCode := 0;
ELSIF #State = 900 THEN
    #State := 900;
ELSIF #StopReq THEN
    #State := 0;
ELSE
    CASE #State OF
        0:
            IF #StartEdge AND NOT #AtPosition THEN
                #State := 10;
            END_IF;
        10:
            IF #MoveTimer.Q THEN
                #ErrorCode := 2;
                #State := 900;
            ELSIF #AtPosition THEN
                #State := 20;
            END_IF;
        20:
            IF NOT #AtPosition THEN
                #ErrorCode := 3;
                #State := 900;
            ELSIF #InspectTimer.Q THEN
                #State := 30;
                // 20 -> 30에서 한 번만 증가, 상한 포화
                IF #CountValue < DINT#2147483647 THEN
                    #CountValue := #CountValue + 1;
                END_IF;
            END_IF;
        30:
            #State := 30;
        ELSE
            #ErrorCode := 99;
            #State := 900;
    END_CASE;
END_IF;

// 4. 대기에서만 횟수 초기화. Start와 동시 입력은 증가 없음
IF #ClearCount AND (#State = 0) THEN
    #CountValue := 0;
END_IF;

// 5. 출력은 전이 이후 한 곳에서 결정
#MotorCmd := (#State = 10) AND #Permit AND NOT #StopReq AND NOT #Reset;
#InspectCmd := (#State = 20) AND #AtPosition AND #Permit
               AND NOT #StopReq AND NOT #Reset;
#Busy := (#State = 10) OR (#State = 20);
#Done := (#State = 30);
#Fault := (#State = 900);
#StepNo := #State;
#FaultCode := #ErrorCode;
#CompletedCount := #CountValue;
#MoveElapsed := #MoveTimer.ET;
#InspectElapsed := #InspectTimer.ET;
ClearCount는 전이 후 State=0일 때만 동작합니다. 대기에서 Start와 ClearCount를 동시에 입력해 State=10으로 바뀌면 초기화되지 않습니다. 작업자는 대기에서 ClearCount를 먼저 처리하고 해제한 뒤 Start를 입력합니다.

타이머는 전이 전 State로 평가하고 출력은 전이 후 State로 평가합니다. 새 단계의 타이머는 다음 호출부터 시작할 수 있으며, 단계가 끝난 스캔에는 경과값이 잠시 남았다가 다음 호출에서 초기화될 수 있습니다. 화면 관찰 시 이 차이를 고려합니다.

아래는 인스턴스 DB가 생성된 뒤 SCL 주기 프로그램에서 호출하는 예시입니다. 주기 프로그램이 LAD/FBD이면 FB 호출 상자를 삽입하고 같은 태그를 연결합니다. 한 인스턴스를 서로 다른 OB에서 중복 호출하지 않습니다.

코드 읽기 — 횟수와 타이머가 틀어지는 이유

설계 포인트이 코드의 처리실수하면 생기는 현상
시작 에지PrevStart를 매 호출 갱신Stop 해제 시 눌린 Start로 재시작
타이머 호출모든 스캔에서 IN을 명시해 호출이전 경과값·Q가 의도와 다르게 남음
상태 저장FB Static의 StateTemp 사용 시 호출 간 상태 불확실

정상 운전 시험 — 한 사이클을 끝까지

순서입력 조작기대 결과
1모든 입력 FALSE → Permit=TRUE, Reset=TRUEStep=0, Fault=FALSE, 모든 운전 명령 OFF
2Reset=FALSE, ClearCount=TRUE 후 FALSE완료 횟수 0, 대기 유지

정지·고장·복귀 시험

시험방법기대 결과
일반 정지이송 또는 검사 중 StopReq=TRUEStep=0, 운전 명령 OFF
정지 해제Start를 계속 TRUE로 둔 채 StopReq=FALSE새 에지 없으므로 대기
이송 시간 초과AtPosition=FALSE로 이송 5초 초과900, FaultCode=2
검사 위치 상실Step=20에서 AtPosition=FALSE900, FaultCode=3
허가 상실Permit=FALSE900, FaultCode=1 (새 고장 시)
최초 고장 유지코드 2 고장 후 Permit=FALSE코드 2 유지
고장 상태에서 정지900에서 StopReq=TRUE고장 유지
허가만 복구Permit=TRUE로만 변경고장 유지, 자동 재개 없음
허가 없는 ResetPermit=FALSE, Reset=TRUE고장 상태 유지
고장 해제Permit=TRUE, Reset=TRUE 후 FALSE0, FaultCode=0, 횟수 유지
검사 중 ResetPermit=TRUE에서 Reset=TRUE0, 검사 취소, 완료 횟수 증가 없음

경계 조건

  • AtPosition이 이미 TRUE인 상태에서는 시작하지 않습니다.
  • Start와 StopReq 동시 입력은 정지 우선입니다.
  • StopReq 상태에서 발생한 새 Start 에지는 저장해서 나중에 실행하지 않습니다.
  • 완료 시점과 StopReq가 같은 스캔이면 정지 우선이므로 완료 횟수를 올리지 않습니다.
12

감시 테이블과 문제 해결

감시 테이블에 LabSeq의 모든 입력, StepNo, FaultCode, MotorCmd, InspectCmd, Done, CompletedCount, 두 경과값을 추가합니다. 내부 DB 값을 수정할 때도 시뮬레이션 또는 승인된 독립 실습 장치인지 확인합니다.

증상확인 순서
시작하지 않음Permit·StopReq·Reset·AtPosition → Start 새 에지 → FB 호출
시작 직후 고장FaultCode와 이전 입력 상태 확인
검사가 끝나지 않음타이머 인스턴스·매 스캔 호출·AtPosition 확인
완료 횟수가 계속 증가증가문이 20→30 전이에만 있는지 확인
Reset 후 바로 재시작PrevStart가 Reset 중에도 갱신되는지 확인
타이머 컴파일 오류편집기에서 TON 멀티인스턴스를 생성하고 호출 구문 비교
동작 결과가 스캔마다 다름같은 인스턴스 중복 호출·같은 태그 중복 대입 확인
증상을 감추려고 최대 사이클 시간을 늘리거나 타이머의 내부 구조를 강제로 쓰지 않습니다. 컴파일 메시지·현재 입력·상태·실제 호출 경로부터 확인합니다.
13

확장 과제 — 단계 제어를 재사용 가능하게

  1. 고정된 T#5s와 T#2s를 Time 입력 MoveLimit·InspectTime으로 바꿉니다. 0 이하·과도한 설정값의 정책도 정의합니다.
  2. 고장 발생 시 StepNo를 별도 ErrorStep에 저장하고 Reset까지 유지합니다.
  3. 정지 시 이어서 재개하는 일시정지 요구사항을 새로 설계합니다. 위치·타이머 재개·시작 조건을 표로 먼저 작성합니다.
  4. 가상 장치 두 대를 만들고 같은 FB를 서로 다른 인스턴스 DB로 호출합니다. 상태와 타이머가 서로 독립적인지 확인합니다.
  5. 완료 횟수의 Retain 필요성을 검토합니다. CPU 재시작 후 운전 명령이 자동으로 복원되지 않도록 정책을 작성합니다.
추가 기능을 작성하기 전 정상·예외·우선순위·출력을 표로 갱신하고 시험 항목도 함께 추가합니다. 프로그램 줄 수보다 요구사항과 시험 결과의 일치가 중요합니다.
14

확인 문제와 실습 제출

1. State를 Temp가 아니라 Static으로 선언하는 이유는?

다음 FB 호출에서도 현재 단계를 유지해야 하기 때문입니다. 전원 차단 후 유지 여부는 Retain 등 별도 설정과 구분합니다.

2. TON에 각각 다른 인스턴스가 필요한 이유는?

이송과 검사 타이머의 경과값과 상태가 독립적으로 저장되어야 하기 때문입니다.

3. 완료 횟수를 State=30인 모든 스캔에서 올리면?

완료 상태를 유지하는 동안 매 스캔 증가합니다. 이 예제는 20→30 전이에서 한 번만 올립니다.

4. StopReq와 Reset은 같은 기능인가요?

아닙니다. StopReq는 진행 취소이며 고장을 해제하지 않습니다. Reset은 Permit이 있을 때 고장 코드를 해제하고 대기로 돌립니다.

5. 일반 Bool Permit이 안전 기능을 대신하나요?

아닙니다. 예제의 일반 실행 허가일 뿐이며 안전 인증 기능이 아닙니다.

11주차 핵심 정리

  • 시퀀스는 정상 순서와 예외·우선순위를 함께 설계합니다.
  • 상태·타이머는 FB 인스턴스에 독립적으로 저장합니다.
  • 타이머와 시작 에지는 매 스캔 평가하고 출력은 한 곳에서 결정합니다.
  • 정지는 취소, Reset은 초기화, 새 Start는 시작이라는 역할을 구분합니다.
  • 완료 횟수는 완료 상태 매 스캔이 아니라 완료 전이에서 증가시킵니다.
  • 컴파일 성공과 실제 동작 검증은 다릅니다.
