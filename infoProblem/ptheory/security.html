3. 암호화와 전자서명

평문은 보호 전의 읽을 수 있는 데이터, 암호문은 키와 알고리즘으로 변환한 데이터입니다.

대칭키: 같은 비밀키를 양쪽이 공유

공개키 방식과 전자서명은 목적이 다르다

공개키 암호화의 기본 개념수신자의 공개키를 이용해 암호화하고, 대응하는 개인키로 복호화합니다. 공개키는 공개해도 되지만 개인키는 비밀로 보관합니다.
전자서명서명자는 개인키로 메시지에 대한 서명을 만들고, 검증자는 공개키로 확인합니다. 서명은 출처·무결성 확인을 돕지만 그 자체가 메시지 내용을 숨기지는 않습니다.
해시입력에서 고정 길이 요약값을 계산합니다. 해시는 암호화가 아니므로 보통 원문 복호화 기능이 없고, 해시값만으로 누가 만들었는지 증명하지도 않습니다.
현대 HTTPS 참고: TLS는 공개키 기법을 사용해 통신 상대 인증과 세션 키 설정을 돕고, 실제 데이터는 효율적인 대칭키 방식으로 보호합니다. TLS 1.3의 구체적 절차는 단순히 “공개키로 전체 파일을 암호화”하는 방식과 다릅니다. RFC 8446
비밀번호는 일반 SHA-256 해시만 저장하면 안 됩니다.비밀번호 전용 해시/KDF를 사용하고, 계정마다 고유한 salt를 적용하며 계산 비용을 충분히 높여야 합니다. NIST는 salted password hashing과 오프라인 추측 공격에 대한 저항을 권고합니다. NIST SP 800-63B

4. 인증과 접근 통제

로그인 확인과 권한 부여는 별개의 단계입니다. 로그인에 성공했다고 모든 데이터에 접근할 권한이 생기는 것은 아닙니다.

접근 통제권한을 결정하는 기준떠올릴 말
DAC 임의적자원 소유자가 다른 사용자 권한을 지정소유자가 재량
MAC 강제적보안 등급과 중앙 정책에 따라 접근 결정등급·정책
RBAC 역할 기반사용자에게 역할을 주고 역할에 권한을 연결역할별 권한
ABAC 속성 기반사용자·자원·환경 속성과 정책을 함께 평가조건·속성
최소 권한 원칙: 업무에 필요한 최소 권한만 부여하고, 역할이나 업무가 바뀌면 불필요한 권한을 회수합니다. 가능하면 다중 인증과 피싱 저항성이 있는 인증 수단도 검토합니다.

5. 네트워크 보안

보안 장비는 서로 대체재가 아니라, 다른 위치와 방식으로 트래픽을 통제하거나 살펴보는 도구입니다.

기술주 역할쉽게 구분
방화벽 Firewall정책·주소·포트 등에 따라 트래픽 허용 또는 차단통과 규칙
IDS침입 징후를 감시·탐지하고 경고탐지·알림
IPS트래픽을 검사해 공격으로 판단한 흐름을 차단하는 등 대응탐지 + 차단
WAF웹 애플리케이션 요청·응답을 중심으로 규칙 검사웹 계층 보호
VPN공용 네트워크 위에 인증·암호화된 가상 통신 터널 구성보호된 연결
TLS / HTTPS전송 중 통신의 인증·기밀성·무결성을 지원통신 구간 보호
보안 장비가 있어도 전부 안전해지는 것은 아닙니다.HTTPS/TLS는 통신 경로를 보호하지만 감염된 단말이나 취약한 서버 애플리케이션을 고쳐 주지는 않습니다. VPN도 연결 터널을 보호할 뿐, 사용자의 권한을 자동으로 올바르게 관리하지 않습니다.

원격 명령 접속은 SSH, SSH 기반 파일 전송은 SFTP, 웹 통신은 HTTPS를 사용합니다. 평문 프로토콜이나 검증되지 않은 인증서를 그대로 사용하는 상황을 피하세요.

6. 웹·데이터베이스 보안

웹 입력값은 데이터로 다뤄야 합니다. 이를 명령이나 코드로 해석하게 만들면 인젝션 계열 취약점이 생길 수 있습니다.

취약점무슨 일이 생기나?핵심 방어와 주의
SQL 인젝션입력 문자열이 SQL 명령의 일부로 합쳐져 의도하지 않은 조회·변경을 유발매개변수화 쿼리로 명령 구조와 값을 분리. 정렬 기준·테이블명처럼 매개변수화할 수 없는 식별자는 허용 목록으로 제한. 입력 검증만으로 대체하지 않음.
XSS공격자 데이터가 다른 사용자의 브라우저에서 실행 가능한 스크립트·콘텐츠로 처리출력 위치에 맞는 인코딩, 안전한 DOM API, 필요한 경우 검증된 HTML 정화. 입력 검증은 보조 통제.
CSRF로그인한 브라우저가 공격자 유도 요청에 세션 쿠키를 자동 포함상태 변경 요청에 서버 검증 CSRF 토큰, 출처 검사, SameSite 쿠키 등 계층 방어. GET 요청으로 상태를 바꾸지 않음.
디렉터리 탐색경로 조작으로 앱이 허용한 디렉터리 바깥 파일을 요청고정된 기준 경로 안에서 정규화·검사하고 허용 목록과 파일 권한을 적용.
쿠키 Cookie브라우저가 저장하고 조건에 맞으면 요청에 함께 보내는 작은 값입니다. 세션 ID를 담을 수 있습니다.
세션 Session웹 서버가 로그인 상태 등 사용자별 상태를 관리하는 방식입니다. 브라우저는 세션 ID를 쿠키로 보낼 수 있습니다.
쿠키 속성: Secure는 HTTPS 연결에서만 보내도록 하고, HttpOnly는 일반 자바스크립트의 쿠키 읽기를 제한하며, SameSite는 일부 교차 사이트 요청에서 쿠키 전송을 제한하는 데 도움을 줍니다. SameSite는 CSRF 토큰을 항상 대체하는 완전한 방어책이 아닙니다. 출처: OWASP Session Management.
SQL 인젝션 예방의 핵심 답: 사용자 입력을 SQL 문자열에 직접 이어 붙이지 말고, 매개변수화 쿼리로 값을 바인딩합니다. OWASP는 동적 값에 대한 쿼리 파라미터화와 동적 식별자의 허용 목록을 권고합니다. SQL Injection Prevention · XSS Prevention · CSRF Prevention.

8. 보안 관리와 백업

여러 방어선을 겹쳐 사고 가능성과 피해를 낮춘다

자산과 취약점어떤 시스템·데이터를 보호하는지 파악하고 취약점을 찾아 조치합니다.
접근 통제와 교육최소 권한, 강한 인증, 사회공학 인식 교육을 적용합니다.
로그와 모니터링로그인, 권한 변경, 중요 데이터 접근을 기록하고 이상 징후를 살핍니다.
백업과 복구 계획자료를 분리해 백업하고, 실제 복원할 수 있는지 시험합니다.

백업 3가지: 무엇을 기준으로 바뀐 파일을 담나?

백업 방식담는 범위복구할 때특징
전체 Full선택한 전체 데이터를 복사해당 전체 백업 사용복구 단순, 저장·시간 부담 큼
증분 Incremental직전 백업 이후 바뀐 데이터전체 백업 + 그 뒤 모든 증분 백업각 백업 작지만 복구 단계가 많음
차등 Differential마지막 전체 백업 이후 바뀐 데이터전체 백업 + 가장 최근 차등 백업시간이 지나면 차등분이 커질 수 있음
위험 Risk: 위협이 취약점을 악용해 손실을 일으킬 가능성과 영향을 함께 고려한 개념입니다. 시험에서는 위험을 위협·취약점·영향의 관계로 이해하고, 단순히 취약점 하나와 같은 말로 취급하지 마세요.

9. 확인 문제

선택지를 눌러 정답과 짧은 해설을 확인하세요.

문제 1. 개인정보가 허가 없이 유출되었다면 주로 침해된 보안 요소는?
정답: 기밀성 — 허가되지 않은 사람이 정보를 보았기 때문입니다.
문제 2. 같은 비밀키로 암호화와 복호화를 수행하는 방식은?
정답: 대칭키 암호 — AES가 대표 예입니다.
문제 3. 개인키로 서명하고 공개키로 검증하는 것은?
정답: 전자서명 — 메시지 기밀성을 위한 암호화와는 목적이 다릅니다.
문제 4. 침입 징후를 탐지하고 경고하는 시스템은?
정답: IDS — IPS는 탐지 결과에 따라 차단 등 대응을 수행합니다.
문제 5. SQL 인젝션을 막는 가장 대표적인 방법은?
정답: 매개변수화 쿼리 — 명령 구조와 사용자 입력값을 분리합니다.
문제 6. XSS 방어의 핵심 원칙으로 가장 알맞은 것은?
정답: 데이터를 표시하는 위치에 맞게 출력 인코딩하고 안전한 DOM 사용을 적용합니다.
문제 7. 직전 백업 이후 바뀐 자료만 저장하는 방식은?
정답: 증분 백업 — 복구할 때 전체 백업 뒤의 각 증분본이 필요합니다.
문제 8. 같은 종류의 비밀번호 두 개를 조합한 것은 다중 요소 인증인가?
정답: 아닙니다 — 두 비밀번호 모두 지식 요소이므로 서로 다른 인증 요소의 조합이 아닙니다.
한 줄 복습: 기밀성은 “누가 보나”, 무결성은 “바뀌었나”, 가용성은 “쓸 수 있나”. IDS는 탐지, IPS는 탐지 후 차단. SQLi는 쿼리 파라미터화, XSS는 문맥별 출력 인코딩, CSRF는 요청 위조 방어.
